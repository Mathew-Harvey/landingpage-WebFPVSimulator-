# Brand assets

The creative that already exists across the three repositories, what each
piece is for, and how to regenerate it rather than redraw it.

The rule running through all of it: **almost everything here is generated
output.** Editing the file instead of rerunning the script is how two
versions of one thing end up shipped, and in two places a lint exists
specifically to catch somebody doing it.

## The sticker pack

`stickers/index.html` in this repository. Twenty two stickers as inline SVG
in the house palette.

| | |
| --- | --- |
| chibi whoop | hinomaru sea |
| railway town | peeker |
| pen and ink gate | wave strip |
| brush banner | wave peeker |
| sakura branch | bubble whoop |
| visor strip | livery strip |
| manga corner | wave crest |
| hinomaru hatch | goggle view |
| petal wake | cut vinyl wordmark |
| wakaba | ema plaque |
| pilot | speech bubble |

Each one downloads two ways: a **PNG at 600 dpi** rendered from the vector
in the tab, or the **SVG with the fonts embedded**.

It is one file on purpose. The three faces it sets its type in are base64 in
a style block, the export code reads them back out of it, and nothing on the
page fetches anything. So it works saved to a desktop, mailed to somebody,
or handed to a printer as an attachment, with no server behind it and no
network.

That property is the reason this is the most immediately usable marketing
artifact in the three repositories. A print shop can be sent the file.

Eight of them are slapped on the glass over the film on the landing page:
pilot, brush banner, pen and ink gate, goggle view, railway town, bubble
whoop, wakaba and ema plaque. Each is a link back to the pack.

`src/stickers-data.js` is **generated** from the pack by `node
scripts/stickers.js` and holds the SVG of every sticker the film asks for,
verbatim, plus the font block once. `npm run lint:page` regenerates it in
memory and fails if the copy on disk differs, so an edit to the pack that is
not followed by a rerun cannot ship two versions of one sticker.

## The share card

`og.png`, 1200 by 630, present in all three repositories and served from all
three mounts. Regenerated by `node scripts/og.js` in the simulator's
repository.

**It is a photograph of the product, not a poster about it.** `scripts/og.js`
drives `scripts/shots.js`, which drives the actual page in headless Chromium
with the real renderer, so the picture cannot drift out of agreement with
the product the way a mockup would. The frame is the title screen on the
race field with the menu hidden, leaving the wordmark over the world: the
lit start gate centre, the parked quad in the near left, flags and markers
running away behind.

`--graphics=high` is passed deliberately, because headless Chromium
rasterises on the CPU and boot would otherwise detect a slow machine, drop
the preset, and produce a card whose quality depended on who regenerated it.

Compositing a designed card was considered and rejected against the brief.
If a designed card is ever wanted for a campaign it is a new thing, not a
replacement for this one.

**There is no animated card and there will not be.** Facebook, Messenger, X,
LinkedIn, WhatsApp, Slack and iMessage all flatten a link preview to a
still, and X takes frame one of a GIF. Discord is the only place that would
animate one. This is written into `DEPLOY.md` so the question does not get
asked again.

## The icons

`icon.svg`, `favicon.ico` and `apple-touch-icon.png`, in all three
repositories, all generated by `scripts/icons.js` in the simulator's
repository. **Regenerate, do not edit.** From a checkout of the simulator
beside the target:

```
node scripts/icons.js <colour> ../<target>/public
```

Each page's icon takes the accent that page is built out of, because the
icon is seen next to that page's title:

| Page | Icon colour | Why |
| --- | --- | --- |
| Simulator | sakura | Its wordmark's FPV is sakura, and sakura is the family's chrome colour |
| Track builder | amber | Every armed tool, selected object and readout in it is amber |
| Board | mint | Its chrome is sakura like the simulator's, and two identical icons defeat the point, so it takes the colour it paints a record in |
| Landing page | cream | The front door owns no product's accent and gets the other half of the wordmark |

**There is a second mapping and it disagrees on every row.** The landing
page's three cards use mint for the simulator, sakura for the builder and
amber for the board. Neither is wrong: a card sits in a row of three on one
page and only has to differ from its two neighbours, while an icon has to
survive being looked at beside the page it belongs to. Taking the cards'
mapping would have put a sakura icon on the amber page.

Anybody producing collateral that shows the three products side by side
should pick one of the two mappings knowingly, and say which. `DEPLOY.md`
in the simulator's repository tabulates the same four and is the copy a
deploy is read from.

The `.ico` and `.png` cannot carry a licence notice, which is a limit of
those formats rather than an exemption anybody chose. The `.svg` does.

## The palette

The screen palette, from `index.html` in this repository, and the same
tokens in the simulator and the board.

| Token | Hex | What it is for |
| --- | --- | --- |
| `cream` | `#f3ead4` | Lit type |
| `sakura` | `#e8a8b8` | Chrome |
| `amber` | `#ffd45c` | An instrument |
| `mint` | `#7dffb4` | A record, and the only thing you press |
| `slate` | `#9db3c8` | Type that should recede |
| `dim` | `#8a9a86` | Quieter still |
| `deep` | `#141c16` | The ground |
| `panel` | `#1a241c` | Panels |
| `ink` | `#0c120e` | The darkest ground |

Two rules in it are functional rather than decorative and should survive
into any collateral. **Mint is the only thing you press**, so mint on
anything that is not an action is a lie the whole product tells
consistently everywhere else. **Amber is an instrument**, so amber on
decoration reads as a readout.

Gates are amber at rest, mint at the start and finish, and neon green for
the one a run wants next. That is functional colour and it is untouched by
any theming.

The **printed vinyl palette** is a different set and lives in `BANNER` in
`src/art/banners.js`. It is tabulated in `artwork-spec.md`, because the
people who need it are sponsors' designers checking their mark against the
banner it will sit on.

## The wordmark

WebFPV, with FPV in sakura and the rest in cream on the landing page's own
mark. The simulator's wordmark is the one element in the share card that
survives being shrunk to the 500 pixels a social feed actually renders,
which is why it is the one thing left on screen in that frame. Worth
knowing before anybody designs something that relies on smaller type
surviving a feed.

## The film

The landing page itself is a four minute film, scrolled rather than played,
rendered live with three.js. It is not a video file and there is no video
file to hand anybody.

If a campaign needs a video, it has to be captured from the page, and the
existing tooling for exactly that is `scripts/shots.js` in the simulator's
repository, which drives headless Chromium against the real pages. That is
how the share card is made and it is the honest route to a clip.

simulator**. That is worth saying in a pitch and it is easy to miss.

## Licence, which constrains what can be handed out

Everything in the three repositories is **GPLv3**. The simulator is a
derivative work of Betaflight, whose control loop is compiled into it, so
this is not a choice anybody can revisit.

For marketing purposes the consequence is narrow but real: the stickers, the
icons and the page source carry that licence. A sponsor who wants to
reproduce the artwork in their own material should be given permission in
writing for their own mark and told plainly what the licence covers for
everything else. Do not assume a sponsor's legal team will read the header
before their agency uses the file.
